DUTs would be SCL cells of sufficient notability, and a bunch of primitives that are lacking foundry open-source e-test coverage (e.g. there's no data on vias/contacts, there's no coverage for thin oxide native nmos at all, there's no coverage for (admittedly kinda DRC-breaking though IMO that's ERC domain and should be waived for at least test structures if modeling is good enough) short channel native NMOS, a LOT of devices lack mismatch characterization (e.g. shottkey diodes are just a start)). Leo Moser (mole99) 2026-09-24 6:58 a.m.
@Martin Schoeberl Let me address your two issues. 1. Nix is recompiling the binaries This should not happen if you have the FOSSi Nix cache set up. Please follow the installation instructions at https://librelane.readthedocs.io/en/stable/installation/nix_installation/index.html, making sure you set up https://nix-cache.fossi-foundation.org as an additional Nix cache. You can verify that the Nix cache has been set up correctly by starting a Nix shell with LibreLane (nothing should recompile): $ nix shell github:librelane/librelane $ librelane --smoke-test 2. ghdl-bin is not available for aarch64-linux The ghdl-bin package (the VHDL simulator) is only available for x86_64-linux and aarch64-darwin. That is unfortunately a limitation of GHDL as it only targets these platforms afaik: https://github.com/ghdl/ghdl/releases/tag/v6.0.0 ghdl-bin is required by wafer.space because the Nix flake in the gf180mcu-project-template includes cocotb, and cocotb requires ghdl-bin during the check phase. We can try to workaround this problem: You can simply remove the cocotb package from the Nix flake: https://github.com/wafer-space/gf180mcu-project-template/blob/0de7e394337a1f7f5303ac7a3681bf2481b58176/flake.nix#L71 This should allow you to enable the Nix shell and run LibreLane. However, you won't be able to run any simulations with cocotb. Another workaround would be to disable the check phase in cocotb and remove ghdl-bin when the platform is aarch64-linux. Of course, then we can't be sure that cocotb will work as expected, but it will probably be fine. Let me know if you would like to give this a try.
