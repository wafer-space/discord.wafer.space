Looks like I'm putting some chips on the table regarding wirebonding exchange formats. Currently have a few problems we need to solve. Right now everything is built around humans reading pictures. And in the age of AI, I think our formats should become more human-centric anyways.

The premise

A picture is already the accepted exchange format today. So keep the picture as an SVG (which is just XML under the hood), and embed wirebonding data directly as key/value pairs in the raw XML. Proposed format is myboard.wb.svg
Humans get what they want. Machines can read what they want.
What we've got so far:
  • Footprint export: generates 3D models you can add to your board alongside your GDS (see attached). I'm also working on embedding the SVG data directly into the footprint itself.
  • GDS import: finds the paths in your GDS and uses their names to help you create symbols and nets.
  • Multiple die and stacked die support.
  • Any bond topology: board to die, die to die, and everything in between.
  • import/export of wb.svg files directly
  • ...plus a bunch of other fun little tools. Links and more info:

htamas 2026-11-17 3:19 p.m.
  • As Sylvain mentioned, SVG is tricky, especially when you want to read an SVG file written by a different program. You need to be careful with picking the right subset. AFAIU you only want one-way compatibility, i.e. you want general SVG software to read .wb.svg, but you will only support reading files written by .wb.svg aware software. If so, I would make it more clear in the docs.
  • Do you support non-axis-aligned rectangles as landing pads? They are useful for laying out pads along a circular arc to optimize max bond wire length vs. pad count, or to equalize the lengths of the wires.
  • What's the suggested workflow? You draw the footprint in kicad, load it into the webapp, add the bond wires, export the .wb.svg and use it to regenerate the footprint? Is the .wb.svg the single source of truth? Shall I treat the kicad footprint as autogenerated? What happens if I need to manually edit the pad placement later on?
  • Can I generate the footprint, 3d model, bondlist etc. from an unattended CI script instead of the webapp?
  • I usually put some "extras" in my cob footprints: die attach pad, ground/power rings, silkscreen for glob top area, courtyard to keep other components away, fanout wires to connect the landing pads to the top-level grid etc. Where should they live? I wouldn't put them into an autogenerated footprint file because I don't want them to be overwritten. I don't want to bloat the .wb.svg spec with such features either. It would make sense to include the autogenerated footprint in my hand-drawn footprint, but kicad doesn't support nested footprints. Should I place two footprints on top of each other in the pcb layout? That might be the best solution, but I feel kind of meh.

Vik Olliver 2026-11-21 3:37 a.m.
Couple of approaches: (1) Dipping the probe and using it as a pen. This produces dots 20-4μm diameter and you get about 100 dots before you need to re-dip the probe (depends on viscosity, exact probe dimensions, phase of moon etc.) (2) Use a negative photoresist and a UV head. This doesn't need a thin film like chip production does (though it can work with one) because it only sets the resist between the probe tip and the substrate. The height of the probe determines the thickness of the solidified resist. This can get down to 4-5μm and is considerably faster than (1).
